Paso 2

Instalar

irm https://claude.ai/install.ps1 | iex

# Windows · CMD
curl -fsSL https://claude.ai/install.cmd -o install.cmd && install.cmd && del install.cmd

BLOQUE 3

Cómo pedir trabajo

Lo que recomienda Anthropic

Principio 1

Un empleado brillante… y nuevo

No conoce vuestras normas ni vuestra forma de trabajar.

Regla de oro: enseña tu prompt a un compañero que no sepa nada de la tarea. Si él se confundiría, Claude también.

Principio 2

Explica el porqué

Solo la orden

"No uses console.log."

Con el motivo

"Los logs de producción se revisan en auditorías, así que no escribas datos personales en ellos. Usa el logger del proyecto."

Con el motivo, Claude acierta también en los casos que no habías previsto.

Principio 3

Sé específico

VagoEspecífico
"Añade tests para foo.py""Escribe un test para foo.py para el caso en que el usuario no ha iniciado sesión. Sin mocks."
"Arregla el bug del login""El login falla tras caducar la sesión. Revisa src/auth/, sobre todo el refresco del token. Escribe un test que lo reproduzca y luego arréglalo."
"El build falla""…arréglalo y comprueba que el build pasa. Ataca la causa, no silencies el error."

Principios 4 y 5

Pide la acción · Dale cómo comprobarla

Lo que pides es lo que hace

"¿Puedes sugerir cambios…?"
→ sugiere y no toca nada

"Cambia esta función para…"
→ la cambia

Que pueda verificar

  • Tests
  • Un build
  • Una captura para comparar

Pide evidencia, no afirmaciones.

Principio 6

Primero el plan

Explorar→Planificar→Implementar→Guardar
  • Shift+Tab hasta ver ⏸ plan mode on: propone sin tocar nada
  • Si puedes describir el cambio en una frase, sáltate el plan

Principio 7

Tono normal, en positivo

Evita

"CRÍTICO: DEBES usar X SIEMPRE"

"No uses listas"

Mejor

"Usa X cuando…"

"Responde en párrafos"

Los modelos actuales siguen muy bien las instrucciones: las mayúsculas les hacen exagerar.

Contexto, alcance y cómo comprobarlo.Si falta uno de los tres, Claude lo rellenará adivinando.

⚡ Actividad · La primera versión de la app12 min
  1. Escribe en el chat cómo pedirías hoy la primera versión de Cadena de frío
  2. Reescríbela con la plantilla (en la guía del proyecto hay una versión posible)
  3. Shift+Tab a plan mode y lánzala · al aprobar el plan, elige aceptar ediciones
  4. npm start → comprueba los dos ejemplos de la especificación
Contexto:    qué pasa y por qué importa
Alcance:     dónde trabajar y qué NO tocar
Hecho cuando: cómo comprobamos que está bien
Entrega:     qué quiero ver al final

Memoria de proyecto

Lo que Claude lee al empezar cada sesión

CLAUDE.md

Las reglas de vuestro proyecto, en un fichero

FicheroPara quién
./CLAUDE.mdTodo el equipo · va en el repositorio
./CLAUDE.local.mdSolo tú, en este proyecto · no se comparte
~/.claude/CLAUDE.mdSolo tú, en todos tus proyectos
subcarpeta/CLAUDE.mdSe carga al trabajar en esa carpeta

CLAUDE.md

Qué poner: solo lo que Claude no puede deducir

No lo puede deducir → ponlo

  • Comandos de build, test y lint
  • Convenciones propias
  • Zonas prohibidas
  • Cómo verificar
  • Cómo se revisan e integran los cambios

Lo deduce, o no debe ir → fuera

  • Lo que se ve leyendo el códigolo deduce
  • Documentación largatapa lo importante
  • Tareas de esta semanamañana ya no es verdad
  • Secretos y contraseñasacaban en el repositorio

Menos es más

Corto, o no lo leerá bien

  • Menos de 200 líneas
  • Para cada línea: "si la quito, ¿Claude se equivocaría?"
  • @docs/arquitectura.md importa otro fichero… pero también se carga entero
¿Usáis también Cursor u otros agentes? Claude Code lee AGENTS.md si no hay CLAUDE.md. Para una sola fuente: un CLAUDE.md que contenga @AGENTS.md.

📖 Guía del proyecto · Sesión 1, paso 4

⚡ Así debería quedar tu CLAUDE.md15 min
## No tocar
- docs/especificacion.md — la cambia una persona, no Claude. Si crees que
  hay que cambiarla, dilo.
- No añadas dependencias de npm sin preguntar.

## Verificación antes de dar algo por terminado
1. Arranca la app y comprueba los ejemplos de la especificación.
2. Enseña lo que has comprobado; no digas "funciona" sin decir cómo.
3. Di qué no has podido verificar.

## Convenciones
- Código y nombres en español.
- Nada de datos de pacientes: solo equipos y lecturas.
- Los datos no salen del navegador: nada de analítica ni servicios externos.

Importante

Consejos no son reglas

CLAUDE.md

Instrucciones que Claude normalmente sigue

Hooks y permisos

Reglas que se aplican siempre, las siga o no

Lo que no puede pasar nunca (producción, .env…) necesita una regla, no solo una línea en CLAUDE.md. → Sesión 2

BLOQUE 5

Tu primer comando

Un prompt que se repite, convertido en fichero

Slash commands

Un fichero = un comando

.claude/commands/revisa-cambios.md  →  /revisa-cambios

  • El contenido del fichero es el prompt
  • Va en el repo: todo el equipo tiene el mismo comando
  • En la sesión 3 lo convertiremos en skill
Regla de la tercera vez: si escribes el mismo prompt por tercera vez, merece ser un comando.
⚡ Actividad · Crea /revisa-cambios8 min

Antes, un punto de guardado: git add -A · git commit -m "Primera versión". Luego pídeselo a Claude (petición en la guía, paso 5). Así debería quedar .claude/commands/revisa-cambios.md:

---
description: Revisa los cambios sin commitear contra CLAUDE.md
disable-model-invocation: true
---
Estos son los cambios sin commitear del repo:

!`git diff HEAD`

Revísalos contra las reglas de CLAUDE.md. Para cada problema:
archivo, qué regla incumple y cómo arreglarlo. No cambies nada.

Foco adicional: $ARGUMENTS

Cómo funciona

Las tres piezas

!`git diff HEAD`Se ejecuta antes: Claude recibe el diff real
$ARGUMENTSLo que escribes detrás: /revisa-cambios céntrate en seguridad
disable-model-invocationSolo lo lanzas tú, no Claude por su cuenta
Windows sin Git: añade shell: powershell en la cabecera.
