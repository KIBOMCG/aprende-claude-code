Capa 2

Modos de permisos

ModoSin preguntarte puede…Para
ManualSolo leerTrabajo sensible, código desconocido
Aceptar edicionesLeer y editar ficherosIterar sobre código que revisas

Shift+Tab para cambiar · claude --permission-mode manual para arrancar en uno

Auto mode

Qué bloquea por defecto

  • Descargar y ejecutar código (curl | bash)
  • Enviar datos sensibles fuera
  • Despliegues y migraciones a producción
  • Borrar ficheros que ya existían
  • git push --force
  • git reset --hard y similares
  • Cambiar permisos o infraestructura compartida
  • Fusionar una PR que nadie ha aprobado
Es un filtro, no una garantía. Lo que no puede pasar nunca necesita una regla.

Plan mode

Pensar antes de tocar

  1. Shift+Tab hasta ⏸ plan mode on, o empieza el prompt con /plan
  2. Claude explora y propone un plan. No edita nada
  3. Ctrl+G abre el plan en tu editor para cambiarlo
  4. Al aprobarlo eliges cómo sigue: revisando cada cambio o con menos preguntas
Regla práctica: si puedes describir el cambio en una frase, no hace falta plan.
BLOQUE 2

Reglas de permisos

Permitir, preguntar o prohibir

Dónde viven

Ficheros de configuración

FicheroPara quién
Configuración gestionadaToda la organización · la pone IT · manda sobre todo
.claude/settings.local.jsonSolo tú en este proyecto · no se comparte
.claude/settings.jsonTodo el equipo · va en el repositorio, junto al código
~/.claude/settings.jsonSolo tú, en todos tus proyectos

De arriba abajo, de más a menos prioridad. /permissions muestra todas las reglas y de qué fichero viene cada una.

Tres listas

deny · ask · allow

{
  "permissions": {
    "deny":  ["Read(./.env)"],
    "ask":   ["Bash(git push *)"],
    "allow": ["Bash(npm test *)"]
  }
}
  • Se evalúan en orden: deny, luego ask, luego allow
  • Un allow no puede abrir una excepción en un deny

Patrones útiles

Cómo se escriben

Read(./.env)No leer el .env (tampoco con cat, head…)
Read(./secrets/**)Nada dentro de secrets/
Edit(./src/generated/**)No editar código generado
Bash(git push *)Cualquier git push
Bash(npm run *)Cualquier script de npm
WebFetch(domain:github.com)Consultar ese dominio

Límites

Lo que una regla no cubre

  • Las reglas de Bash miran el texto del comando: git -C . push no coincide con Bash(git push *)
  • Read no frena a un script que abre ficheros por su cuenta (Python, Node…)
Para bloquear a nivel de sistema: el sandbox (/sandbox). Funciona en macOS, Linux y WSL2; en Windows nativo, no.

BLOQUE 3

Hooks

Comprobaciones automáticas

Hooks

Tu código, en momentos clave

EventoCuándoEjemplo
PreToolUseAntes de una acciónFrenarla con un mensaje propio
PostToolUseDespués de una acciónFormatear o pasar el lint al editar
StopCuando Claude va a terminarNo dejarle acabar con los tests en rojo
NotificationCuando te necesitaAvisarte en el escritorio

Cómo funcionan

Salir con código 2 = "no"

  • El hook es un comando: tu script, tus tests, tu lint
  • Si sale con código 2, la acción se frena y lo que escribas en la salida de error le llega a Claude para que lo corrija
  • En Stop, código 2 significa: "todavía no has terminado"
Criterio de Anthropic: para prohibir, reglas de permisos. Para automatizar comprobaciones, hooks.

Ejemplo · macOS y Windows con Git Bash

No terminar con los tests en rojo

.claude/settings.json

"hooks": {
  "Stop": [
    { "hooks": [ { "type": "command",
        "command": "bash \"$CLAUDE_PROJECT_DIR/.claude/hooks/verifica.sh\"" } ] }
  ]
}

.claude/hooks/verifica.sh

out=$(npm test 2>&1) || {
  echo "Los tests fallan. Corrigelos antes de terminar:" >&2
  echo "$out" | tail -n 40 >&2
  exit 2
}

Ejemplo · Windows sin Git Bash

Lo mismo, en PowerShell

"hooks": {
  "Stop": [
    { "hooks": [ { "type": "command", "command": "powershell.exe",
        "args": ["-NoProfile", "-ExecutionPolicy", "Bypass", "-File",
                 "${CLAUDE_PROJECT_DIR}/.claude/hooks/verifica.ps1"] } ] }
  ]
}

.claude/hooks/verifica.ps1

$out = npm test 2>&1 | Out-String
if ($LASTEXITCODE -ne 0) {
  [Console]::Error.WriteLine("Los tests fallan. Corrigelos antes de terminar:")
  [Console]::Error.WriteLine($out)
  exit 2
}
⚡ Actividad · Tu primer hook15 min
  1. Pídele que añada la regla de los límites (8,0 °C en una nevera de 2 a 8 está en rango) a la especificación: te preguntará, apruébalo tú
  2. Pide los tests, solo los tests: el de 10 € entre tres debería fallar
  3. Pídele el hook, diciéndole tu sistema (petición en la guía; así debería quedar, en D21 y D22)
  4. Reinicia y comprueba que aparece en /hooks
  5. Pídele que lo arregle sin tocar los tests: no podrá terminar hasta que pasen

Con cuidado

Antes de confiar en un hook

  • Un hook ejecuta código en tu máquina: revisa los hooks de un repo antes de usarlo
  • Si el hook nunca se cumple, Claude lo intenta hasta 8 veces seguidas y luego para
  • Que sea rápido: se ejecuta cada vez que salta el evento
  • /hooks lista los hooks activos y de qué fichero viene cada uno

Experimentar sin miedo

Checkpoints y /rewind

Checkpoints

Volver atrás

Cada mensaje que envías crea un punto de control. /rewind o EscEsc para volver:

Código y conversaciónTodo como estaba en ese punto
Solo conversaciónVuelves a ese mensaje y conservas el código
Solo códigoDeshaces los cambios y conservas la conversación
Resumir desde aquíComprime la conversación para liberar contexto

Límites

Checkpoints no son control de versiones

Deshace

Lo que Claude cambió con sus herramientas de edición

No deshace

Lo que hizo un comando (rm, migraciones, npm install…) ni tus cambios fuera de Claude

Checkpoints para probar. Control de versiones para decidir.En Cadena de frío usamos Git. En vuestro trabajo, el que uséis: la idea es la misma.

Gobierno del equipo

Qué se decide para todos

Configuración gestionada

Lo que puede imponer IT

  • Reglas deny que nadie puede saltarse
  • Que solo se pueda entrar con la cuenta de la organización
  • Desactivar el auto mode o el modo sin permisos
  • Modelos permitidos y canal de actualizaciones
  • Obligar a usar el sandbox (macOS, Linux, WSL2)
Se despliega como fichero, por registro o GPO, o desde el panel de administración de Claude.
